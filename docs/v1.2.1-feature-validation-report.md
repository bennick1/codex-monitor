## Why structural pairing cannot prove the requested tier

The following source chain is decisive:

1. `update_settings_if` commits thread configuration and constructs both its
   configuration copy and settings snapshot.
   [session/mod.rs L1906–1923](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/session/mod.rs#L1906-L1923)
2. `new_turn_with_sub_id_if` then applies `service_tier_for_turn` only to the
   Turn's configuration copy. It returns the original `commit.snapshot`.
   [turn_context.rs L1076–1112](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/session/turn_context.rs#L1076-L1112)
3. `turn_input` passes that snapshot to `emit_applied`; snapshot emission is
   conditional on a thread-settings update, independently of the per-turn tier.
   [turn_input.rs L139–178](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/session/turn_input.rs#L139-L178)
4. `emit_applied` publishes `thread_id` and `thread_settings: snapshot`, without
   the per-turn override.
   [thread_settings.rs L123–138](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/session/thread_settings.rs#L123-L138)

Consequently, both counterexamples are permitted by the source:

| Thread snapshot | Unpersisted per-turn override | Tier requested for the Turn |
| --- | --- | --- |
| `priority` | `default` | Standard |
| `default` | `priority` | Fast |

These are source-permitted counterexamples, not claims that a local sample
actually used an override. Both can satisfy the proposed six structural rules.
Thus the rules establish **snapshot-to-Turn structural association**, but do
not establish the Turn's effective requested tier. Confirmed effective
`priority → Fast Turn` pairs: **0**. Confirmed effective
`default → Standard Turn` pairs: **0**.

Upstream emits the settings snapshot before spawning the task, which emits
`task_started` before the observed `turn_context`. The observed order is
therefore consistent with upstream, but does not repair the semantic gap.
[turn_input.rs L340–363](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/session/turn_input.rs#L340-L363),
[regular.rs L48–51](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/tasks/regular.rs#L48-L51)

Only `event.msg` is persisted; the outer submission correlation ID is not part
of the settings event. Standalone settings updates and checkpoints can also
emit snapshots, so one snapshot does not inherently mean one new Turn.
[session/mod.rs L2551–2554](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/session/mod.rs#L2551-L2554),
[thread_settings.rs L20–28, L111–146](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/core/src/session/thread_settings.rs#L20-L146)

## Replay, archive, fork and identity stop conditions

- Never carry a setting across file boundaries or beyond the one proven
  immediate Turn interval. A B window does not mark every later Turn Fast.
- Reject copied/forked history when the active owner and provenance cannot be
  established. Upstream explicitly says copied settings retain their original
  logical owner.
  [protocol.rs L2193–2200](https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/protocol/src/protocol.rs#L2193-L2200)
- Do not splice contexts or completions by a bare Turn hash across files.
  Twenty-one context Turn hashes recur across files. Five A sources also have
  explicit fork copies; only their original, continuous source was eligible.
- One context hash occurs in eight different threads without its own start,
  completion, or settings. Those records provide no boundary evidence. A
  later verified real completion may establish a fresh interval; this does
  not retroactively validate the ambiguous prefix.
- One thread has two non-overlapping file segments. No setting or terminal
  boundary was carried between them.
- Archive location alone neither proves nor disproves continuity. In the
  observed archived priority case, missing owner, repeated settings, abort,
  and absent context independently stop attribution.
- Abort, rollback, timeline reset, missing/mismatched owner, overlapping Turns,
  unverified terminal boundaries, conflicting tiers, and nonmonotonic relevant
  ordering stop the current association. After reset, require a fresh,
  verified real terminal and a fresh pre-start snapshot; do not reuse history.
- Repeated same-value snapshots remain candidate-safe. Mixed values remain
  Ambiguous; no latest-value-wins rule was assumed.
